# مهارة: سير عمل GitHub الاحترافي

هدفها: كل تغيير يصل إلى GitHub يكون **نظيفاً، مفهوماً، وآمناً، وقابلاً للتشغيل**.

## 1. قبل أي تعديل: افهم الحالة
```bash
git status -sb          # الفرع الحالي والملفات المعدّلة
git log --oneline -10   # آخر التغييرات
git fetch origin        # جلب آخر نسخة من GitHub
```
- لا تعمل مباشرة على `main`. أنشئ فرعاً بوصف واضح:
  `git checkout -b feature/login-page` أو `fix/upload-crash`

## 2. فحص صحة المستودع (Repo Health Check)
تحقق من هذه النقاط وأبلغ عن أي مشكلة:

| الفحص | لماذا مهم |
|---|---|
| أسماء الملفات بلا مسافات أو أخطاء (مثل `runtime. txt` ← `runtime.txt`) | المنصات (Heroku وغيرها) لن تتعرف على الملف |
| ملف التشغيل يطابق الأمر في `Procfile` (مثلاً `web: python app.py` يحتاج ملف `app.py` موجوداً) | وإلا يفشل النشر |
| ملفات بايثون تنتهي بـ `.py` | للاستيراد والأدوات والتلوين |
| وجود `README.md` | يشرح المشروع وطريقة تشغيله |
| وجود `.gitignore` (`__pycache__/`, `.env`, `*.db`, `venv/`) | لمنع رفع ملفات مؤقتة أو حساسة |
| `requirements.txt` يحتوي كل المكتبات المستوردة فعلاً | وإلا يفشل التثبيت |

## 3. فحص الأمان قبل الدفع
```bash
git diff --cached | grep -nEi "(api[_-]?key|secret|password|token)\s*[:=]"
```
- **ممنوع** رفع: `.env`، مفاتيح API، كلمات مرور، قواعد بيانات حقيقية.
- الأسرار تُقرأ من متغيرات البيئة: `os.environ["JISR_SECRET"]` — ولا تضع قيمة افتراضية سرية في الكود.
- إذا رُفع سرّ بالخطأ: **غيّره فوراً** (حذفه من الكود لا يكفي، فهو باقٍ في التاريخ).

## 4. تأكد أن الكود يعمل
```bash
python -m py_compile *.py         # أخطاء الصياغة
pip install -r requirements.txt   # التبعيات
python -m pytest -q               # إن وُجدت اختبارات
```
لا تدفع كوداً لم تشغّله.

## 5. Commit صغير ورسالة واضحة
- commit واحد = فكرة واحدة.
- الصيغة (Conventional Commits):
  ```
  <type>: <وصف قصير بصيغة الأمر>

  لماذا هذا التغيير (اختياري)
  ```
  الأنواع: `feat` ميزة، `fix` إصلاح، `docs` توثيق، `refactor` إعادة هيكلة، `chore` صيانة، `test` اختبارات.
- أمثلة جيدة: `fix: rename runtime. txt to runtime.txt` — `feat: add CSV export for orders`
- أمثلة سيئة: `update`، `Create Jisr`، `asdf`
- أضف الملفات بالاسم (`git add app.py`) بدل `git add .` لتجنب رفع ملفات غير مقصودة.

## 6. الدفع
```bash
git push -u origin <branch-name>
```
إذا رُفض الدفع لأن الفرع البعيد تقدّم: `git pull --rebase origin <branch-name>` ثم ادفع مجدداً. **لا تستخدم `--force` على فرع يعمل عليه غيرك.**

## 7. Pull Request
اكتب وصفاً بهذا الشكل:
```markdown
## ماذا يفعل هذا التغيير؟
## لماذا؟
## كيف اختبرته؟
## لقطات شاشة (إن كان في الواجهة)
```
- PR صغير (أقل من ~400 سطر) يُراجَع أسرع وأدق.
- اربطه بالـ issue: `Closes #12`.

## 8. مراجعة الكود (Code Review)
عند مراجعة PR لغيرك ركّز بالترتيب على:
1. **الصحة**: هل يعمل؟ حالات حدّية؟ أخطاء؟
2. **الأمان**: إدخال المستخدم، SQL injection، رفع الملفات، الأسرار.
3. **الوضوح**: أسماء مفهومة، دوال قصيرة.
4. **الأسلوب** أخيراً — ولا تعطّل PR بسبب ذوق شخصي.

## الناتج المتوقع
عند تنفيذ المهارة، قدّم للمستخدم:
- قائمة المشاكل المكتشفة في المستودع (من البند 2 و3) مع الإصلاح المقترح لكل منها.
- رسالة commit مقترحة.
- وصف PR جاهز للنسخ إن طُلب.
